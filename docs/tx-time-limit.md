# 送信時間の制限と PTT の後始末

2026-11-04〜05 に行った送信の安全対策のうち、送信時間の制限に関わる検討と変更をまとめる。対象のコミットは `2073196`、`f521528`、`4beb94e`、`8d5d401`、`b59e818`。いずれも PC 上のテスト(偽のピンと偽の I2C)で確認しただけで、実機では確認していない。

## 1. 目的

送信(PTT のオン)が、意図した時間を超えて続かないようにする。考えた原因は次の 3 つ。

| 原因 | 例 | 対策の置き場所 |
|---|---|---|
| 送出が終わらない | DMA やペーシングのタイマーが止まり、送信波形の終わりが来ない | `TxGate` の時間の上限と `AfskTx.finish()`(§2) |
| 後始末が実行されない | 例外や Ctrl-C で、PTT を切る処理より前に抜ける | PTT を最初に切る順序(§3) |
| ファームウェアが止まる | Python のハング | ウォッチドッグ(§4、未実装) |

時間の上限は「プログラムが動いているときの保護」で、ファームウェアが止まったときには働かない。止まったときの保護はウォッチドッグだけで行い、回路側に送信を止める機能は設けない(オーナーの決定)。

## 2. 送信時間の上限

### 上限の値

- `core/txgate.py` の `APRS_MAX_MS = 5000`(5 秒)が、1 回の送信の上限の既定。APRS のビーコン 1 回を想定した値で、確定ではない
- 実際の上限は、送信のたびに「波形の長さ + 200ms(`_DONE_MARGIN_MS`)」と 5 秒の短い方にする(`TxGate.key(limit_ms)`)。1200bps の APRS フレームは、フラグ 300ms と末尾 30ms を含めても、送信バッファ `TX_BUFFER_MS = 1500` に収まる長さに限られる。通常は 2 秒未満で切れる
- 音声の送信は未実装。音声には 180 秒の上限を別に持つ予定

### 止め方

- `TxGate.expired()` は、PTT を入れてから上限を過ぎたかを返すだけで、自分では止めない
- `AfskTx.finish()` が呼ばれるたびに `expired()` を見る。過ぎていれば `abort()` で PTT を切り、DMA と PWM を止めてから `TxTimeout` を投げる。呼び出し側の待ちのループ(`while not finish()`)は、DMA が終わらなくても抜けられる
- 以前は `Station._beacon` の `while not tx.finish()` に上限がなく、DMA が止まると PTT がオンのまま待ち続けた

## 3. PTT を残さない後始末

- `TxGate.unkey()` と `AfskTx.abort()`、`AfskTx.close()` は、最初の行で PTT を切る。以降の処理で例外が起きても、PTT は切れている
- `Station._beacon` は `finally` で `tx.abort()` を呼ぶ。以前の `finally` は LED と表示しか戻さなかった
- `Station.close()` は、受信の停止より先に送信を閉じる。以前は受信の停止(`Receiver.stop`)の後に `tx.close()` を呼んでいた。受信の停止の待ちに上限がなく、受信側のコアが止まると PTT を切る処理に届かなかった。送信中に Ctrl-C が 2 回来ても、2 回目が受信の停止の中で起きて `tx.close()` を飛ばし、PTT が High のまま REPL に戻る経路があった
- `Receiver.stop` の待ちに上限 500ms(`_STOP_TIMEOUT_MS`)を付けた
- 送信クロック(Si5351 の送信出力)を止める `tx_off()` が送信の終わりで失敗しても、後始末は続ける。PTT は切れているが、以後の送信は再起動まで「TX clock off failed」で拒否する

## 4. ファームウェアが止まったとき(未実装)

ウォッチドッグは未実装で、次の設計で進める予定。

- タイムアウトは 3 秒程度。RP2350 の上限は約 16 秒だが、APRS 1 回の上限 5 秒より短くする
- フィードは局のメインループだけで行う。送信の待ちのループの上限は §2 の時間の上限が担う
- 長い待ち(`station.main` の最大 300 秒の `time.sleep`、GNSS の初期化、SD のマウントと書き込み)は、分割してフィードするかを実測で決める
- 開発中の実行(`dev.py run` のマウント中など)ではリセットすると応答しなくなるので、有効にするのはリリースの起動だけにする

### リセット後に PTT が切れるか(未確認)

ウォッチドッグのリセットで GP2(PTT)が Low に戻るかは、RP2350 の設定次第で、実機で確認する。

- RP2350 のパッドが既定(Hi-Z、入力無効、プルダウン)に戻るのは、電源投入、ブラウンアウト、RUN ピン、SWD のリセット。ウォッチドッグのリセットの範囲は `PSM_WDSEL` と `RESETS_WDSEL` で決まり、既定値はすべて 0(RP2350 データシート §9.7、§12.9)
- pico-sdk の `watchdog_enable` はリセットコントローラごとリセットする設定にするので、GP2 の出力は切れる見込み。MicroPython の `machine.WDT` が同じ関数を使うかは未確認
- パッドの分離ラッチで、リセット前の High がラッチされる可能性も否定できない
- 対策: `boot.py` の先頭で GP2 を Low にする。ウォッチドッグを有効にした後に `PSM_WDSEL` を読み戻し、想定と違えば送信を拒否する。送信部の TX_EN には外付けの GND への経路(プルダウン)を残す
- 実機での確認(無線機ボードを外して行う): `PSM_WDSEL`、`RESETS_WDSEL`、`CHIP_ID` を読む。GP2 を High にしてウォッチドッグを発火させ、Low になるまでの時間をオシロで測る

### 再起動の扱い

- 起動時に送信クロックを止められない(`tx_off()` の I2C が失敗する)ときは、何もせず無限ループし、ウォッチドッグの再起動を繰り返す(オーナーの決定)。GP2 は I2C より先に Low にする
- ウォッチドッグが未実装の今は、再起動にならず、そこで止まったままになる(PTT は切れたまま、送信なし、受信と表示もなし)
- ウォッチドッグのリセットでは `hw/restart.py` の失敗回数が増えないので、異常な再起動の後に最初のビーコンを 90 秒待つ処理が効かない。`machine.reset_cause()` などでの判定を追加する必要がある

## 5. 関連する未解決の点

- Si5351B は送信用 PLL のロック外れを検出できない(AN619 は LOL_B を Si5351A/C のみとしている)。送信の判定は初期化と水晶の状態、待ち時間(仮の 10ms)で行う
- ウォッチドッグのリセットでは Si5351 は初期化されず、送信クロックが出たまま残る。PTT が切れていても、空中線端子に約 −40〜−20dBm 漏れる見積もり(回路の手計算、未測定)。受信と同じ周波数なら受信できないので、起動の最初に Si5351 の全出力を止める

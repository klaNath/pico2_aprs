# FX.25 送信

## 1. 方針

- **送信だけを実装する。受信側(相関タグの検出と RS 復号)は、この機では実装しない**(オーナーの決定、2026-11-16)
- RS(255,239) は扱わない。内側の AX.25(両端のフラグ込み、ビットスタッフ後)が 128 バイトを超えるフレームは、従来の AX.25 で送る
- 既定は無効(`config.FX25_TX = False`)。有効にするには `src/config_local.py` に `FX25_TX = True` と書く

受信側の扱い: FX.25 の局を受けても、誤りがなければ内側が普通の HDLC フレームなので、既存の `Deframer` がそのまま復号する。誤りがあるフレームを RS で救う処理は無い。

## 2. 対応するモード

チェックバイト 16 バイト(最大 8 バイトの訂正)の 3 種。

| タグ | RS(n, k) | データ欄 k | 内側の最大 | 送信ブロック(タグ込み) |
|------|----------|-----------|-----------|----------------------|
| 0x04 | RS(48, 32) | 32 バイト | 32 | 56 バイト(0.37 秒) |
| 0x03 | RS(80, 64) | 64 バイト | 64 | 88 バイト(0.59 秒) |
| 0x02 | RS(144, 128) | 128 バイト | 128 | 152 バイト(1.01 秒) |

- 内側に収まる最小のモードを選ぶ(`Fx25Tx.prepare()`)。収まらなければ 0 を返し、`AfskTx.build()` が従来の方式で作る
- 「内側」の大きさは、先頭と末尾の 0x7E、FCS、ビットスタッフを含むバイト数(端数は切り上げ)。ゼロだけの 126 バイトのフレームがちょうど 128 バイト。0xFF が多いとスタッフで増える
- 典型的な Mic-E ビーコン(約 60 バイト)は RS(80,64) になる

## 3. 線上の形

```
[前置フラグ 0x7E × N][タグ 8 バイト][データ欄 k バイト][チェック 16 バイト][後置フラグ × M]
```

- 全体を連続した NRZI で送る。タグ、データ欄、チェックにはビットスタッフをしない
- タグは 64 bit 値の下位バイトから、各バイトは LSB から送る
- データ欄は `0x7E` + ビットスタッフ済みフレーム(FCS 込み)+ `0x7E` で、残りは 0x7E のビット列で埋める。閉じフラグがバイト境界に来ない場合は、閉じフラグの次のビットからフラグのビット列を続ける(バイト境界で区切り直さない)
- RS は GF(2^8)、原始多項式 0x11D、生成多項式の根は α^1 〜 α^16(fcr = 1、prim = 1)
- 短縮符号の符号語は 255 バイトで、`[データ k バイト][ゼロ 239 - k バイト][チェック 16 バイト]`。**ゼロはデータの後ろ**(前ではない)。チェックは符号語の最後に置くので、ゼロも符号化に含める

仕様は Dire Wolf の `fx25_init.c`、`fx25_send.c`、`fx25_rec.c` で確認した。**FX.25 の仕様書(PDF)は取得できず、読んでいない。**

## 4. 実装

| ファイル | 内容 |
|----------|------|
| `src/modem/fx25.py` | `Fx25Tx`: `prepare(frame)` でデータ欄を作り、`write(out, pre, post, level)` で RS を計算してレベル列(NRZI、1 バイト 1 ビット)を書く |
| `src/hw/afsk_tx.py` | `AfskTx(..., fx25=True)`。`build()` がフレームごとに FX.25 か従来方式かを選ぶ。FX.25 にした数は `tx.fx_used` |
| `src/config.py` | `FX25_TX` |
| `src/station.py` | `AfskTx` へ `FX25_TX` を渡す。ログに ` fx25` と出す |
| `src/tx_demo.py` | `FX25_TX` に従う |

- `src/tnc/` は micro-aprs 由来の生成物なので触らず、FX.25 は `src/modem/` に自作で置いた(Dire Wolf のコードは写していない)
- メモリは `Fx25Tx` を作るときに約 1 KB を 1 回だけ確保する。`prepare()` と `write()` は確保しない(NRZI の状態を `self._lv` に持ち、タプルを返さない)
- RS の符号化は純 Python。viper にはしていない

## 5. 負荷と送信時間(実機、Pico 2、2026-11-15)

| 項目 | 値 |
|------|-----|
| RS(255,239) 相当の符号化(純 Python、239 バイト分) | 約 50 ms |
| `build()`(FX.25、波形生成を含む) | 184 ms(従来は 112 ms) |
| 約 60 バイトのフレームの音声の長さ | 913 ms(従来 715 ms)。前置フラグ 300 ms を含む |

- 送信バッファ `TX_BUFFER_MS = 1500` に収まる最大は RS(144,128)(前置 300 ms と後置 30 ms を含めて約 1.34 秒)。RS(255,239) を使わない理由の一つ
- ウォッチドッグのループ上限 3 秒([tx-time-limit.md](tx-time-limit.md) §4)に対しても余裕がある
- 送信時間が延びる分、チャネルの占有は増える

## 6. 確かめたこと

- テスト(`tests/test_fx25.py`、PC と実機)
  - タグの値と、64 bit 値としての復元
  - モード選択とスタッフの影響
  - 符号語のシンドロームがすべて 0(テスト側で別に書いた GF 演算)
  - データ欄の配置と、フラグ埋めの位相
  - 変調と復調を通した往復
- 実機(2026-11-16)
  - AX.25 のみ対応の受信機(FT5D)で全パケットがエラーなしで復号できた
  - Dire Wolf で FX.25 として受信できた
